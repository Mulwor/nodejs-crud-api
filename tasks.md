### Необходимо реализовать простой CRUD API, используя базу данных в оперативной памяти и вот следующие технические требования.

1. Реализовать эндпоинт: `api/users`:
    - **GET** `api/users`- для получения всех юзеров
        - Сервер должен отвечать со status code 200 и всеми записями о пользователях
    - **GET** `api/users/{userId}`
        - Сервер должен отвечать со status code 200 и записью с id === userId, если она существует
        - Сервер должен отвечать со status code 400 и соответствующим сообщением, если userId невалиден (не uuid)
        - Сервер должен отвечать со status code 404 и соответствующим сообщением, если записи с id === userId не существует
    - **POST** `api/users` используется для создания записи о новом пользователе и сохранения её в базе данных
        - Сервер должен отвечать со status code 201 и вновь созданной записью
        - Сервер должен отвечать со status code 400 и соответствующим сообщением, если body запроса не содержит обязательных полей
    - **PUT** `api/users/{userId}` используется для обновления существующего пользователя
       - Сервер должен отвечать со status code 200 и обновлённой записью
       - Сервер должен отвечать со status code 400 и соответствующим сообщением, если userId невалиден (не uuid)
       - Сервер должен отвечать со status code 404 и соответствующим сообщением, если записи с id === userId не существует
    - **DELETE** `api/users/{userId}` используется для удаления существующего пользователя из базы данных
        - Сервер должен отвечать со status code 204, если запись найдена и удалена
        - Сервер должен отвечать со status code 400 и соответствующим сообщением, если userId невалиден (не uuid)
        - Сервер должен отвечать со status code 404 и соответствующим сообщением, если записи с id === userId не существует
2. Пользователи хранятся в виде объектов, которые имеют следующие свойства:
    - `id` — уникальный идентификатор (string, uuid), генерируемый на стороне сервера
    - `username` — имя пользователя (string, обязательное)
    - `age` — возраст пользователя (number, обязательное)
    - `hobbies` — увлечения пользователя (массив строк или пустой массив, обязательное)
3. Запросы к несуществующим эндпоинтам (например, some-non/existing/resource) должны обрабатываться (сервер должен отвечать со status code 404 и соответствующим понятным для человека сообщением)
4. Ошибки на стороне сервера, возникающие во время обработки запроса, должны корректно обрабатываться (сервер должен отвечать со status code 500 и соответствующим понятным для человека сообщением)
5. Значение `port`, на котором запущено приложение, должно храниться в файле `.env`
    - Важно: Сам файл .env не должен коммититься в репозиторий, так как это считается небезопасной практикой. Пожалуйста, добавьте файл .env в .gitignore.
    - Вместо этого создайте и закоммитьте файл .env.example, который содержит список требуемых переменных окружения с разумными значениями по умолчанию. Пример содержимого .env.example: `PORT=4000`
6. Должно быть 2 режима запуска приложения (development и production):
    - Приложение запускается в режиме разработки с использованием `nodemon` или `ts-node-dev` (есть npm скрипт start:dev)
    - Приложение запускается в режиме продакшн (есть npm скрипт start:prod, который запускает процесс сборки, а затем запускает собранный файл)
7. Должны быть некоторые тесты для API (не менее 3 сценариев). Пример тестового сценария::
    - Получить все записи с помощью `GET` запроса `api/users` (ожидается пустой массив)
    - Новый объект создаётся с помощью `POST` запроса `api/users` (ожидается ответ, содержащий вновь созданную запись)
    - С помощью `GET` запроса `api/users/{userId}` мы пытаемся получить созданную запись по её id (ожидается созданная запись)
    - Мы пытаемся обновить созданную запись с помощью `PUT` запроса `api/users/{userId}` (ожидается ответ, содержащий обновлённый объект с тем же id)
    - С помощью `DELETE` запроса `api/users/{userId}` мы удаляем созданный объект по id (ожидается подтверждение успешного удаления)
    - С помощью `GET` запроса `api/users/{userId}` мы пытаемся получить удалённый объект по id (ожидается ответ, что такого объекта нет)
8. Должно быть реализовано горизонтальное масштабирование приложения, должен быть npm скрипт start:multi, который запускает несколько экземпляров вашего приложения с использованием Node.js Cluster API (количество экземпляров равно количеству доступного параллелизма - 1 на хостовой машине, каждый слушает на порту PORT + n) с балансировщиком нагрузки, который распределяет запросы между ними (используя алгоритм Round-robin). Например: доступный параллелизм равен 4, PORT равен 4000. При запуске npm run start:multi это работает следующим образом:
    - На `localhost:4000/api` балансировщик нагрузки ожидает запросы
    - На `localhost:4001/api`, `localhost:4002/api`, `localhost:4003/api` воркеры ожидают запросы от балансировщика нагрузки
    - Когда пользователь отправляет запрос на `localhost:4000/api`, балансировщик нагрузки отправляет этот запрос на `localhost:4001/api`, следующий пользовательский запрос отправляется на `localhost:4002/api` и так далее.
    - После отправки запроса на `localhost:4003/api` балансировщик нагрузки начинает снова с первого воркера (отправляет запрос на `localhost:4001/api`)
    - Состояние БД должно быть согласованным между разными воркерами, например:
        - Первый `POST` запрос, адресованный на `localhost:4001/api`, создаёт пользователя
        - Второй `GET` запрос, адресованный на `localhost:4002/api`, должен вернуть созданного пользователя
        - Третий `DELETE` запрос, адресованный на `localhost:4003/api`, удаляет созданного пользователя
        - Четвёртый `GET` запрос, адресованный на `localhost:4001/api`, должен вернуть 404 status code для созданного пользователя
